> 本文是 [PTX 专栏](/ptx/) 第 5 期，对应官方文档 §3.3。

## TL;DR

SM 芯片上除了执行单元，还摆着四类片上存储：每处理器一组 32 位**寄存器**、所有标量核共享的**共享内存**、只读的**常量缓存**、只读的**纹理缓存**（经纹理单元访问）。这四类要分成两组看：寄存器和共享内存是「数据本体就在片上」的存储；常量缓存和纹理缓存是「缓存」，数据本体在片下的 device memory 只读区，只是把只读副本搬上片来加速。收尾一句：local 和 global 是 device memory 的读写区，本体在片下。

## 一、概念铺垫：片上有哪些存储，为什么要分清

上一期拆 SM 的内部结构时，留下一个钩子：一个 SM = 多个 SP 核 + 一个多线程指令单元 + 一块片上共享内存。前两样上一期讲完了，这一期专讲第三样——以及它背后一张更完整的清单。

为什么要单独把「片上有什么存储」拎出来讲？因为访存延迟是 GPU 的头号敌人。一次全局内存访问动辄几百个时钟周期，如果每个线程每次取数都直奔片下的 device memory，SM 再能零开销切换 warp，也填不满这么深的坑。硬件给出的对策是：在 SM 这块芯片上，紧挨着执行单元摆几块又小又快的存储，让最热的数据留在片内。§3.3 就是清点这些片上存储都有哪些、各自服务什么目的。

但「片上」这个词下面，其实藏着两种不一样的东西：一种是**数据本体就在片上**，另一种是**数据本体在片下、只在片上留了个只读副本**。分清这两者，是这一节真正的重点——它决定了一块存储到底「装得下多少数据」，也解释了为什么有些存储容量大、有些却小得可怜。

## 二、文档语义：§3.3 四类片上内存

§3.3 原文很短，核心就一句话：每个多处理器（SM）有下面四类片上内存。先给图，再逐类拆解。

先看这几块存储在 SM 里的相对位置，以及它们和片下 device memory 的关系：

```text
                    ┌──────────────── 一个 SM（流多处理器）────────────────┐
                    │                                                    │
    SP 核 ×N ────────┤   寄存器组：每个 SP 一组本地 32 位寄存器，私有      │
                    │                                                    │
                    │   共享内存 shared memory：所有 SP 共享，片上，可读写 │
                    │   常量缓存 constant cache：所有 SP 共享，只读        │
                    │   纹理单元 ──► 纹理缓存 texture cache：只读          │
                    └──────────────────────────┬─────────────────────────┘
                                               │ 缓存的是片下只读区的副本
                    ┌──────────────────────────▼─────────────────────────┐
                    │                  device memory（片下）              │
                    │     global 读写区 · local 读写区                     │
                    │     constant 只读区（◄── 常量缓存缓存它）             │
                    │     texture  只读区（◄── 纹理缓存缓存它）             │
                    └────────────────────────────────────────────────────┘
```

图里能直接看出一个关键结构：上面那四块在片上，下面 device memory 在片下；四块里，只有寄存器和共享内存的数据本体就在片上，常量缓存和纹理缓存则是对片下两个只读区的「副本缓存」。下面按文档顺序逐类拆。

**第一类，寄存器：每处理器一组本地 32 位寄存器。** 注意文档用的单位是 **per processor**——每个标量处理器核（SP）各自带一组寄存器，而不是整个 SM 共用一组。这正是寄存器「线程私有」的硬件来源：一个线程映射到一个 SP 核上，用的就是那个 SP 自己的寄存器组。文档还给了规格：**32 位**。寄存器是离计算单元最近、速度最快的存储，但也最贵，所以每个线程能分到的寄存器数量有限，这直接制约了一个 SM 能同时住下多少个线程。

**第二类，共享内存：所有标量核共享的「并行数据缓存」。** 文档给共享内存起了两个名字——parallel data cache 和 shared memory，指同一块硬件：一块让 SM 里所有 SP 核并行访问的片上数据缓存，共享内存空间就落在这里。它和寄存器的本质区别在「共享」二字：寄存器各线程私有，共享内存则对同一 block 内的所有线程可见，所以它是线程之间交换数据、协同工作的主战场——第 3 期反汇编里能看到，共享内存的读写前后往往跟着 `bar.sync` 这类同步，因为「共享」必然带来「谁先写谁后读」的协调问题。文档叫它「并行数据缓存」，重点在「并行」：这块缓存被几十个 SP 核**同时**访问，而不是像 CPU 缓存那样主要服务单个核心。这个「并行访问」能力，正是它能把「块内数据共享」做快的硬件前提。

**第三类，常量缓存：只读，缓存片下的常量区。** 文档的措辞很精确：常量缓存是只读的，由所有 SP 核共享，作用是**加速对常量内存空间的读取**；而常量内存空间，是 device memory 的一个**只读区域**。也就是说，常量数据的「本体」在片下 device memory，SM 上的常量缓存只是它的只读副本。这是常量缓存和共享内存最根本的不同：共享内存是本体，写进去就是真的写进去；常量缓存是副本，只能读、不能写。

**第四类，纹理缓存：只读，且前面接了一个纹理单元。** 纹理缓存同样是只读、所有 SP 共享，缓存的是纹理内存空间——device memory 的另一个只读区域。但文档在这里多交代了一句：每个 SM 通过一个**纹理单元（texture unit）**访问纹理缓存，而这个纹理单元「实现了各种寻址模式和数据过滤」。这句点出了纹理和常量的差别：常量缓存就是一块单纯的只读缓存，而纹理这条路在缓存之前还接了一个能做事的硬件单元——它能把归一化坐标、环绕寻址这类寻址方式，以及插值、过滤这类数据变换，在取数的时候一并完成。所以纹理不只是「另一块只读缓存」，而是「缓存 + 一个专用处理单元」的组合。

**收尾一句：local 和 global 是 device memory 的读写区域。** 文档最后补了这句，是为了把边界划清楚：除了上面四类片上存储，剩下的 local、global 两个空间，本体都在片下 device memory，而且是**可读可写**的。对照前面，constant、texture 是片下的**只读**区（被各自的缓存加速），local、global 是片下的**读写**区——「只读还是读写」，是它们被放进不同缓存路径的原因之一。

到这里可以再追问一句：为什么只有 constant、texture 被做成了「缓存」，而 global 没有？答案就藏在文档反复强调的「只读」二字里。缓存意味着「片上这份是片下本体的副本」，副本要成立，前提是本体不会在缓存存续期间被改写——否则副本就过期了。constant、texture 都是只读区，数据不会被 kernel 改写，硬件可以放心地把副本钉在片上反复用；global 是可读写的，数据随时可能被写，一旦做成缓存就要面对「副本和本体不一致」的麻烦，所以 global 没走这条缓存副本的路。只读，才配得上「缓存」这种设计。

把这四类 + 一句收尾放到一起，就能得出本节最该记住的那条分类线：

| 片上存储 | 数据本体在哪 | 读 / 写 | 备注 |
|----------|--------------|---------|------|
| 寄存器 | 片上（每 SP 私有） | 读写 | 32 位，最贴近计算单元 |
| 共享内存 | 片上（所有 SP 共享） | 读写 | 又称并行数据缓存 |
| 常量缓存 | 片下（device memory 只读区） | 只读 | 缓存常量空间的副本 |
| 纹理缓存 | 片下（device memory 只读区） | 只读 | 前面接纹理单元，做寻址与过滤 |

## 三、佐证：地址宽度上的片上/片下之别

§3.3 是硬件模型，讲的是「芯片上摆着什么」。这些硬件在 PTX 里并非一比一可见——尤其两块缓存，对 PTX 是透明的：PTX 只认识「常量空间」「纹理空间」，不认识「缓存」这个硬件概念。所以这一节没有多少反汇编可讲，能佐证的只剩一件事：**共享内存在片上、地址空间小，全局内存在片下、地址空间大，两者的寻址宽度不一样**。

第 3 期已经完整展示过一个同时踩到全局、共享、常量三条路径的内核，这里不再重复，只摘出其中最能说明「片上 vs 片下」的四行（NVCC 13.3.0，`-arch=sm_90a -ptx -O3`；`%r3` 是 `mov.u32 ...::tile` 取出的共享基址）：

```nasm
        mul.wide.s32    %rd5, %r1, 4;               // 全局：i*4 扩成 64 位
        add.s64         %rd6, %rd4, %rd5;           // 全局：in[i] 的 64 位地址
        shl.b32         %r2, %r1, 2;                // 共享：i*4 留在 32 位
        add.s32         %r4, %r3, %r2;              // 共享：tile[i] 的 32 位地址
```

对比这四行就清楚了：同样是算「基址 + i*4」这个字节偏移，全局内存一路用 64 位（`mul.wide.s32` 扩宽 + `add.s64`），共享内存一路用 32 位（`shl.b32` + `add.s32`）。两处 `i*4` 一个用 `mul.wide` 扩宽、一个用 `shl` 原地左移，写法不同反映的不是编译器心情，而是两个空间的地址宽度不同：共享内存在片上、总共就几十到几百 KB，32 位寻址绰绰有余；全局内存在片下 device memory，地址空间大得多，必须上 64 位。

这里要分清一件事：`shl.b32 %r2, %r1, 2` 里的左移，是「乘 2 的幂」的通用强度削减，跟「片上还是片下」无关；真正体现硬件差异的，是「共享全程 32 位、全局全程 64 位」这个宽度之别。

至于另外三样——寄存器、常量缓存、纹理缓存——反汇编里没有新东西可讲：寄存器直接被指令消费、不经过地址计算（第 3、4 期都见过 `%r`/`%rd` 直接做操作数）；`ld.const` 直接按符号名取常量、不绕 64 位地址（第 3 期已讲过）；而「缓存」本身对 PTX 透明，所有指令里没有一条提到「缓存」——因为缓存是硬件实现细节，PTX 的指令只负责声明「读哪个空间」。

## 小结

- SM 的片上存储共四类：**寄存器**（每 SP 一组 32 位，私有）、**共享内存**（所有 SP 共享，可读写）、**常量缓存**（只读）、**纹理缓存**（只读，经纹理单元）。
- 关键分类线：寄存器和共享内存的**数据本体在片上**；常量缓存和纹理缓存是**缓存**，本体在片下 device memory 的只读区。
- 共享内存又称「并行数据缓存」，被所有 SP 核同时访问，是 block 内线程协同的主战场，读写常伴 `bar.sync` 同步。
- 纹理缓存比常量缓存多一个**纹理单元**，负责实现寻址模式和数据过滤。
- local 和 global 是 device memory 的**读写**区，本体在片下；只有只读的 constant/texture 才配得上「缓存」设计。
- 反汇编佐证（完整 PTX 见第 3 期）：共享内存全程 32 位寻址、全局内存 64 位寻址，是「片上小空间 vs 片下大空间」在指令里的直接体现；缓存本身对 PTX 透明。

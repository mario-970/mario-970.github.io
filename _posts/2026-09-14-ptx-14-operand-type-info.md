> 本文是 [PTX 专栏](/ptx/) 第 14 期，对应官方文档 §6.1–6.3。

## TL;DR

一条 PTX 指令由**操作**和**操作数**组成，操作数就是这条指令的输入和输出。每个操作数的类型来自它的声明，必须与「指令模板 + 指令类型」确定的类型**兼容**；兼容则**静默 cast**（不改位、不生成指令），不兼容就必须显式 `cvt`（PTX 没有 C 那种隐式类型转换）。源操作数在文档里记作 `a`、`b`、`c`，目标操作数记作 `d`，谓词操作数记作 `p`、`q`、`r`、`s`。PTX 是 **load-store 机器**：算术指令的操作数必须全在 `.reg` 寄存器空间，内存和寄存器之间靠 `ld`/`st` 搬移，寄存器之间靠 `mov` 拷贝。

## 一、概念铺垫：从「声明」到「使用」

前面几期讲了类型（第 12 期）和变量声明（第 12 期），但那些都是「声明」层面的事——`.u32` 是什么、`.v4 .f32` 怎么声明。这一期补上「使用」这一半：**一个变量声明出来之后，它是怎么作为操作数进入一条指令的？**

任何一条指令，本质都是「从哪里读几个值 → 算一下 → 结果写到哪里」。这几个「读入」和「写出」的槽位，就是**操作数（operand）**。要读懂一条 PTX 指令，得先回答三个问题：每个槽位**期望什么类型**、**值从哪来**、**结果写去哪**。这三个问题正好对应本章 §6.1（类型信息）、§6.2（源操作数）、§6.3（目标操作数）。

理解这一章的关键，是抓住一条贯穿始终的规则：**指令的每个操作数槽位都有类型预期，操作数带来的实际类型要么兼容、要么必须显式转换，没有中间地带**。这条规则决定了为什么有的代码干干净净（`add.s32` 直接吃两个 `.u32` 操作数），有的代码会冒出一堆 `cvt`。

## 二、文档语义：操作数的三条规则

### 先看一张图：一条指令的操作数结构

```text
一条 PTX 指令的操作数结构（§6.2–6.3）

       @%p1          add.s32          %r3,       %r2, %r1
       └─┬─┘         └──┬──┘          └─┬─┘      └──┬──┘
    谓词 guard       指令类型           目标 d      源 a, b
 （条件执行，可选） （决定槽位期望类型）（结果写入） （读取输入）

       mov.u32         %r1,      %tid.x          // 单源单目标
       └──┬──┘         └─┬─┘      └──┬──┘
      指令类型         目标 d      源 a（特殊寄存器，也算寄存器空间）
```

指令类型（如 `add.s32` 里的 `.s32`）是这条指令「是什么类型」，它决定每个操作数槽位**期望**什么类型。目标操作数永远是第一个，源操作数排在后面。

### §6.1 类型信息：兼容则静默 cast，不兼容则必须转

每个操作数的类型**来自它的声明**。一条规则两条推论：

**规则**：操作数类型必须与「指令模板 + 指令类型」确定的类型**兼容**。类型之间**没有自动转换**。

**推论一**：位类型（`.b*`）与**同 size 的任何类型**兼容；同 size 的整数类型（`.u*` 和 `.s*`）互相兼容。

**推论二**：类型不同但兼容的操作数，被**静默 cast** 到指令类型。

这里的「cast」和「convert」是两个不同的动作，务必分清：

| 操作数类型 | 指令类型 | 会发生什么 |
|------------|----------|-----------|
| `.u32` | `.s32`（`add`） | 兼容 → 静默 cast，**不生成指令** |
| `.u32` | `.b32`（`or`） | 兼容 → 静默 cast，**不生成指令** |
| `.u32` | `.f32`（`add`） | 不兼容 → 必须显式 `cvt`，**生成指令** |

**cast（静默重解释）**：只改变「怎么看待这些位」，不改变位本身，不生成任何机器指令。`.u32` 的值拿去当 `.s32` 用，位序列一模一样，只是符号解释变了。

**convert（显式转换）**：真正改变位模式或大小，必须由 `cvt` 指令显式完成。这就是「没有自动转换」的含义——PTX 不会像 C 那样在 `int` 和 `float` 之间偷偷插一条转换指令；你要转，就得自己写 `cvt`。

### §6.2 源操作数：a、b、c，以及 load-store 约束

源操作数在指令描述里统一记作 `a`、`b`、`c`。有四个要点：

**load-store 机器**。PTX 描述的是 load-store 架构：算术（ALU）指令的操作数**必须全在 `.reg` 寄存器空间**声明的变量里。内存里的数据不能直接参与运算，得先用 `ld` 装进寄存器。

**大小一致**。对大多数运算，源和目标的 size 必须一致（`.s32` 配 `.s32`）。`mul.wide` 这类「明确要改变大小」的指令是例外。

**四条搬移指令的定位**。`ld` 和 `st` 在「可寻址状态空间 ↔ 寄存器」之间搬数据；`mov` 在「寄存器 ↔ 寄存器」之间拷贝；`cvt` 负责「类型/大小的转换」，所以它能接受各种类型和 size。

**谓词操作数**。大多数指令有一个**可选的谓词 guard**（`@p`）控制条件执行；少数指令（如 `setp`）还有额外的谓词源/目标操作数。谓词操作数统一记作 `p`、`q`、`r`、`s`。

### §6.3 目标操作数：d，结果写入处

产生单一结果的指令，把结果存进记作 `d`（destination）的字段。这个结果操作数是寄存器空间里的**标量或向量**变量。一句话概括：**目标永远是寄存器**，因为 load-store 架构里，指令的结果先落进寄存器，再由 `st` 写回内存。

## 三、反汇编与讲解：类型兼容与谓词 guard 落地

下面两个内核，一个踩「类型兼容」，一个踩「谓词 guard 和谓词目标操作数」，看它们在真实 PTX 里长什么样。

### 示例一：`.u32` 与 `.s32` 混用，`.b32` 位运算

CUDA 源码：

```cuda
__global__ void typeCompat(int *out, unsigned int a, int b) {  // L1
    out[0] = a + b;                                             // L2
    out[1] = a | b;                                             // L3
}
```

真实 PTX（Compiler Explorer，NVCC 13.3.0，`-arch=sm_90a -ptx -O3`，指令原样贴入）：

{% raw %}
```nasm
.visible .entry typeCompat(int*, unsigned int, int)(
        .param .u64 typeCompat(int*, unsigned int, int)_param_0,
        .param .u32 typeCompat(int*, unsigned int, int)_param_1,
        .param .u32 typeCompat(int*, unsigned int, int)_param_2
)
{
        ld.param.u64    %rd1, [typeCompat(int*, unsigned int, int)_param_0];  // L1: out 指针
        ld.param.u32    %r1, [typeCompat(int*, unsigned int, int)_param_1];   // L1: a (unsigned)
        ld.param.u32    %r2, [typeCompat(int*, unsigned int, int)_param_2];   // L1: b (int)
        cvta.to.global.u64  %rd2, %rd1;           // 参数指针 → 全局地址
        add.s32         %r3, %r2, %r1;            // L2: a+b，指令类型 .s32
        st.global.u32   [%rd2], %r3;              // L2: 写 out[0]
        or.b32          %r4, %r2, %r1;            // L3: a|b，指令类型 .b32
        st.global.u32   [%rd2+4], %r4;            // L3: 写 out[1]
        ret;
}
```
{% endraw %}

三个点一目了然：

**参数声明全是 `.u32`。** 形参 `int *out` 声明为 `.u64`（64 位指针），`unsigned int a` 和 `int b` 都声明为 `.u32`——注意 `b` 明明是 `int`（有符号），参数槽位却用 `.u32`。这正是 §6.1「同 size 整数类型兼容」的体现：参数传递层面 32 位整数不区分符号，符号解释留到运算时才决定。

**`add.s32 %r3, %r2, %r1` 没有配套 `cvt`。** `a + b` 是有符号 `b` 加无符号 `a`，编译结果是一条 `add.s32`，源操作数 `%r2`（`.u32`）、`%r1`（`.u32`）直接当 `.s32` 用，**没有插入任何转换指令**。这就是「兼容则静默 cast」：`.u32` 和 `.s32` 同 size，位序列不变，只是重新解释符号，所以连 `cvt` 都省了。

**`or.b32 %r4, %r2, %r1` 的指令类型是 `.b32`。** 按位或本质不关心符号，编译器选了位类型 `.b32`。两个 `.u32` 源操作数和 `.b32` 兼容（位类型与同 size 任意类型兼容），照样静默 cast。三条指令看下来，没有一条 `cvt`——因为整段代码从头到尾都是「兼容」关系，这是「无自动转换」的正面：不需要转，就不转。

顺带看清了 §6.2/§6.3 的命名：`add.s32 %r3, %r2, %r1` 里，`%r3` 是目标 `d`，`%r2`、`%r1` 是源 `a`、`b`；且所有算术（`add`、`or`）的操作数都是 `%r*` 寄存器——内存访问全靠 `ld.param`、`st.global` 完成，这就是 load-store 机器。

### 示例二：谓词 guard 与「谓词作目标」

CUDA 源码：

```cuda
__global__ void predGuard(int *out, const int *in, int n) {  // L1
    int i = threadIdx.x;                                       // L2
    if (i < n) {                                               // L3
        int v = in[i];                                         // L4
        out[i] = (v > 0) ? v : -v;                             // L5
    }
}
```

真实 PTX（同编译器与参数）：

{% raw %}
```nasm
.visible .entry predGuard(int*, int const*, int)(
        .param .u64 predGuard(int*, int const*, int)_param_0,
        .param .u64 predGuard(int*, int const*, int)_param_1,
        .param .u32 predGuard(int*, int const*, int)_param_2
)
{
        ld.param.u64    %rd1, [predGuard(int*, int const*, int)_param_0];   // L1: out 指针
        ld.param.u64    %rd2, [predGuard(int*, int const*, int)_param_1];   // L1: in 指针
        ld.param.u32    %r2, [predGuard(int*, int const*, int)_param_2];    // L1: n
        mov.u32         %r1, %tid.x;            // L2: i = threadIdx.x（mov 拷贝）
        setp.ge.s32     %p1, %r1, %r2;          // L3: i >= n？→ 结果写入谓词 %p1
        @%p1 bra        $L__BB0_2;              // L3: 若 i>=n，跳过主体（谓词 guard）
        cvta.to.global.u64  %rd3, %rd2;         // in → 全局地址
        mul.wide.s32    %rd4, %r1, 4;           // i*4（字节偏移，wide 例外）
        add.s64         %rd5, %rd3, %rd4;       // in[i] 的字节地址
        ld.global.u32   %r3, [%rd5];            // L4: v = in[i]
        abs.s32         %r4, %r3;               // L5: (v>0)?v:-v → 绝对值
        cvta.to.global.u64  %rd6, %rd1;         // out → 全局地址
        add.s64         %rd7, %rd6, %rd4;       // out[i] 的字节地址
        st.global.u32   [%rd7], %r4;            // L5: 写 out[i]
$L__BB0_2:
        ret;
}
```
{% endraw %}

这段把 §6.2/§6.3 的谓词部分全部串了起来：

**`mov.u32 %r1, %tid.x`——寄存器间拷贝。** `%tid.x` 是特殊寄存器（线程 ID），`mov` 把它拷进普通寄存器 `%r1`，目标 `%r1` 在前、源 `%tid.x` 在后。§6.2 说的「`mov` 在寄存器之间拷贝数据」在这里落地。

**`setp.ge.s32 %p1, %r1, %r2`——谓词作目标操作数。** `setp` 是「设置谓词」指令，它的目标 `%p1` 是一个**谓词类型**的寄存器，不是普通整数/浮点寄存器。`.ge.s32` 表示有符号比较 `i >= n`（编译器把 `if (i < n)` 取反成「不满足就跳过」）。这正是 §6.2 末尾「谓词操作数记作 `p`/`q`/`r`/`s`」的实例——`%p1` 的前缀 `p` 就是谓词操作数的命名约定。

**`@%p1 bra $L__BB0_2`——谓词 guard。** `@` 前缀 + 谓词寄存器，就是 §6.2 说的「可选的谓词 guard 控制条件执行」：`%p1` 为真（即 `i >= n`）才执行 `bra` 跳转，跳过主体。`@%p1` 本身**不是**操作数槽位里的「源」，而是控制这条指令「是否执行」的开关——这是谓词执行（predicated execution）的语法，第 25 期会展开讲。

**`abs.s32 %r4, %r3`——单源单目标。** 三元 `(v > 0) ? v : -v` 被编译器优化成 `abs.s32`（绝对值），源 `%r3`（`v`）、目标 `%r4`，一条指令一个源一个目标，最直观的操作数结构。

**`mul.wide.s32` 是「大小一致」的例外。** 普通指令源和目标 size 一致，但 `mul.wide.s32 %rd4, %r1, 4` 的源是 32 位、结果是 64 位（`%rd4`）——`wide` 明确要求「结果宽一倍」，属于 §6.2「大多数操作 size 一致」里的「大多数」之外的少数。

## 小结

- 操作数类型来自声明，必须与「指令模板 + 指令类型」兼容；**无自动转换**。
- 位类型 `.b*` 与同 size 任意类型兼容；同 size 整数 `.u*`/`.s*` 兼容；兼容则**静默 cast**（不改位、不生成指令）。
- cast ≠ convert：cast 重解释位，convert（`cvt`）改变位/大小，必须显式写。
- 源操作数记作 `a`/`b`/`c`，目标记作 `d`，谓词操作数记作 `p`/`q`/`r`/`s`。
- load-store 机器：ALU 操作数必须全在 `.reg`，内存与寄存器靠 `ld`/`st`，寄存器间靠 `mov`，类型转换靠 `cvt`。
- 反汇编里：`.u32` 参数直接进 `add.s32`/`or.b32`（静默 cast）；`setp` 把谓词写进 `%p1`，`@%p1` 作 guard 控制 `bra` 是否执行。

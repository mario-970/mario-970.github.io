## 二、芯片动态

- **[Get Started with GPU-Accelerated DuckDB Analytics Using the Sirius Core Extension](https://developer.nvidia.com/blog/get-started-with-gpu-accelerated-duckdb-analytics-using-the-sirius-core-extension/)**（11-23 17:09 UTC）：NVIDIA 与 DuckLabs 把 Sirius（威斯康星大学麦迪逊分校与 NVIDIA 合作的开源 GPU 原生 SQL 引擎）做成 DuckDB 核心扩展——`INSTALL sirius; LOAD sirius;` 两条命令即可用，不需要改写 SQL 或改 schema。分工是 DuckDB 负责 SQL 解析与优化、Sirius 把查询计划在 GPU 上执行，不支持的特性自动回退 DuckDB 的 CPU 引擎（扩展本体约 700 MB，需 DuckDB 2.0 与兼容驱动的 NVIDIA GPU）。对算子侧的意义是 GPU 上的扫描/投影/聚合/join 有了一个可直接调用的开源执行后端，其 kernel 覆盖范围与 CPU 回退边界值得关注。
- **[Tackling GPU Bottlenecks in Plane-Wave DFT with K-Point Batching and Mixed Precision](https://developer.nvidia.com/blog/tackling-gpu-bottlenecks-in-plane-wave-dft-with-k-point-batching-and-mixed-precision/)**（11-18 15:00 UTC，此前因脚本缺陷未被收录，本期补录）：VASP 的 OpenACC 移植按 k 点串行处理，小晶胞 + 密 k 点网格时每步数百次小 GPU dispatch 让 launch 开销盖过计算——单原子 Fe 体系 752 个 k 点，在更贵的 GPU 上反而比 CPU 慢 **8×**。NVIDIA 的 Daviator 用批处理 GPU kernel 替换串行内层循环：核心是 batched Davidson 求解器，用批量化 FFT、GEMM 与自定义 kernel 替掉串行循环，SM 占用率从一小部分拉到接近饱和，数据全程留在显存；VASP 仍掌握 SCF 循环、mixing、对称性与 I/O，Daviator 只在明确定义的调用边界接入设备上已有的数据。配套的混合精度执行层对 Davidson 的部分组件用 FP32 算术与存储、收敛敏感步骤保留 FP64 孤岛，在 FP32:FP64 比高的 GPU（如 RTX PRO 6000 的 64:1）上端到端约 **2×** 加速。参考数据集负载上，相对 CPU 最多 **22×** 更快、成本低 **75%**。通过 ALCHEMI VASP 微服务设置 `LDAVIATOR=True`（混合精度再加 `LDAVIATOR_MIXED_PRECISION=1`）启用，现有 VASP 输入无需改动；目前限单节点，非共线自旋与 gamma-only 后续支持。
- **[Enabling Real-Time AI for Scientific Instruments with GPU-Native Data Acquisition](https://developer.nvidia.com/blog/enabling-real-time-ai-for-scientific-instruments-with-gpu-native-data-acquisition/)**（11-19 17:00 UTC，此前因脚本缺陷未被收录，本期补录）：把传感器采集直接做进 GPU，让 AI 在采集回路里实时分析并反过来调整实验。属数据入口侧的动向，不涉及具体 kernel，列为背景备查。

## 三、arXiv 论文（算子内核）

> 本期增量窗口（提交日 ≥ 11-21）返回 **124 条**，未触及 150 上限：11-21 提交 26 条、11-22 提交 31 条、11-23 提交 67 条——上期指出的「11-20 之后投稿尚未进入索引」的周末与周一批次现已全部公告。逐 id 与 `output/` 下全部往期文章比对，124 条均未收录，无重复。按算子开发相关性精选 8 篇。

- **[Fast 4-bit KV-Cache Decoding on Hopper GPUs: Why Existing Kernels Are Slow and How to Fix Them](http://arxiv.org/abs/2611.30027v1)**（`2611.30027`，cs.LG/cs.DC/cs.PF，11-23）：4-bit KV cache 的读取量约为 FP8 的一半，但 Hopper 没有 FP4 硬件、每字节带宽对应的指令发射能力又很紧，4-bit 值只能在软件里解码。实测 H200 上 vLLM 的 NVFP4 KV 路径（FlashInfer decode）只跑到 **10–20%** 显存带宽，比 FP8 慢最多 **1.7×**；NVBit 指令计数指向两个病根——FlashInfer NVFP4 与 Triton UltraQuant 的执行指令量是 Hopper 每字节发射预算的 **2–6×**，且把加载、解码、矩阵乘串行化。作者的 Hopper 原生 kernel 用一个 TMA producer warp 配两个计算 warpgroup 做重叠，在写入时就按解码后布局排 cache，使解码值从寄存器直接喂 Tensor Core，并交换矩阵操作数顺序让小 query 组免填充。H200 上 batch 32–128 达到峰值带宽的 **67–75%**，11 个 shape 上比 XQA 与 FlashAttention-4 所提原生 FP8 中更快者还快 **1.12–1.49×**。接进 vLLM 后，配一套精度配方（K 均值消除 + 旋转、4 个 BF16 sink token、第 0 层保留 BF16），Llama-3.1-8B 在 batch ≥ 8 时每步比 FlashInfer FP8 快 **1.12–1.64×**，可容纳 token 数为 **1.63×**；单卡 H200 的推理型请求流下 99% 达标吞吐是 FP8 的 1.23–1.32×（Qwen2.5-72B 达 1.67–2.20×），prefill 重的流反而慢 7%。五个 7B–32B 模型重复测量与 BF16 KV 无显著精度差。附带一个实用发现：Qwen2 系的推理变体在 FP8 KV 下崩溃，原因是第 0 层 key 均值几乎全来自 key-projection bias（经 RoPE 后仍可从权重直接算出），该层留 BF16 即可恢复 FP8 KV、配合 K 均值消除可恢复 4-bit KV。
- **[DisSparse: Pipelined Top-$p$ Sparse Attention for Long-Context LLM Serving](http://arxiv.org/abs/2611.28522v1)**（`2611.28522`，cs.LG/cs.CL/cs.DC，11-21）：动态稀疏 attention 的事实标准是固定预算 top-$k$——它的块数确定，契合 vLLM 的静态显存分配；但注意力质量在 head/layer/decode step 间分布不均，固定预算要么在尖峰 head 上浪费带宽，要么在弥散 head 上丢上下文。top-$p$（nucleus）能自适应，却因两块系统级障碍难以进生产：块数可变破坏确定性分配、选择 kernel 本身比 attention 还贵。DisSparse 把 top-$p$ 端到端接进 vLLM：把块选择从 scheduler 关键路径上摘下来，用双流流水线把选择延迟藏到层计算背后，并实现单趟基于直方图的 top-$p$ kernel；另观察到块内稀疏（固定大小 KV 块里高/低重要度 token 混放会抬高选择预算），用按 prefill 累积 attention 分数引导的 token 重定位 kernel 处理。多个模型的长/中上下文 benchmark 上，稀疏分析（块选择）比 SOTA top-$p$ 方法快 **1.17–1.80×**，精度损失可忽略，同显存预算下最大 batch 为 dense vLLM 的 **8×**。
- **[ANOR: Scaling Sparse Attention with a GPU-PNM Computing Hierarchy](http://arxiv.org/abs/2611.30417v1)**（`2611.30417`，cs.AR，11-23）：长上下文服务要常驻全部 KV，容易超过 GPU 显存；挂在 CXL 上的 processing-near-memory（PNM）设备能放下整份 cache 并在原地算 attention，但现有 CXL-PNM 的显存带宽远低于 GPU HBM——此前的 PNM-centric 设计把大部分 attention 放在 PNM 上算，结果 PNM 成瓶颈、GPU 空等。ANOR 改按「GPU 为主、PNM 兜底」分工：利用稀疏 attention 的选择局部性，把大部分 attention 用「近期被选中条目」的 GPU 侧 cache 计算，只有 miss 的部分交给 PNM 直接处理，GPU 的 cache 更新因此可与当步执行解耦；有界 cache 更新策略把更新量卡在后续步骤命中率饱和的位置，减少面向 GPU 的链路流量；片上 Early Streaming Buffer（ESB）在 PNM 计算 attention 时截获 KV 并流回 GPU，在带宽不匹配的前提下避免大部分冗余 DRAM 读；自适应 cache-factor 按服务负载调 GPU cache 大小，平衡命中率与 batch。两个模型、三种长上下文 agentic 负载上，decode 吞吐平均比 HiSparse 高 **2.3×**、比 PNM baseline 高 **2.0×**。
- **[Near-Far Attention: Region-Aware Sparse Retrieval for Long-Context LLM Decoding](http://arxiv.org/abs/2611.30554v1)**（`2611.30554`，cs.LG，11-23）：稀疏 attention 省了算力，但 token 选择本身带来打分与排序开销，且统一的 page 打分忽略了近端与远端上下文的关联差异。NFA 在 prefill 阶段用轻量门控估计器标出 decode 时可整块跳过的区域（额外开销 < 密 prefill 的 1%）；对其余区域，免标定的子空间提取器给出 page 级与 token 级打分共用的紧凑特征（无需离线校准）；再由距离感知的两级选择器对近 page 与远 page 分别打分，在共享预算下联合排序候选 token。跨模型族、参数量与 GQA/MLA 架构，整体任务质量与全 attention 相当；Qwen3-8B 在 512K 上下文下，相对 FlashInfer 最高 **5.49×** 算子加速、**2.97×** 整模型 decode 加速（已含选择开销）。
- **[One Structure Is Enough: Record-Native Tiles for Evolving Sparse Matrices on GPUs](http://arxiv.org/abs/2611.30159v1)**（`2611.30159`，cs.DC，11-23）：流式图等持续变化的稀疏矩阵，在 GPU 上通常要「一份 CSR/ELL/SELL 打包格式做计算 + 一份独立 buffer 收更新」，再周期性 merge/重建/换格式。RecTile 的测量显示这套拆分多数时候不必要：每个 tile 就是一条有序数组，元素是 12 字节的边记录，存储格式直接兼作计算格式。碎片化矩阵（本工作负载下每 tile 1–21 个非零）耗时是最佳 format-pinned slab tile 的 **0.56–1.21×**，tiled 布局比整矩阵 cuSPARSE CSR 快最多 **21×**；中等密度下专用 slab 在其目标模式上更快，但到 25% 密度两者收敛。相对最强的静态 baseline 整矩阵 cuSPARSE COO 在 **1.1–1.6×** 以内，而 COO 无法原地更新；RecTile 不存 per-tile 设备元数据，实际占用下 tile 更小。全 GPU 的 ingest 流水线应用 insert/delete/modify 批次可达 **2900 万边/秒**，是 host 路径的 **4.5×**；精确 DP oracle 在全部测试负载上都不选择 fold，而常规 fold 启发式要多花 **4–15×** GPU 时间、最多 **4×** 持久设备存储。五个演化图负载（含删除密集流）上时间-存储权衡全面改善；在每 tile 1220 条记录的稠密压力流上它仍最快，fold 方案峰值持久存储少 1.3× 但耗时多 3.9×。
- **[Zarc: Exact Nearest Neighbors over a Billion Vectors in Seconds](http://arxiv.org/abs/2611.29252v1)**（`2611.29252`，cs.DC/cs.DB/cs.IR/cs.LG，11-22）：精确 kNN 位于机器学习系统的关键路径上——从最新 LLM 的稀疏 attention 到长上下文记忆、训练数据去重。穷举 GPU 搜索对每个 query 扫全量，近似索引则返回不精确的邻居。近期方法用廉价的半精度「距离下界证明」跳过大部向量，但只能在单卡装下全量数据时成立。Zarc 的想法是：GPU 显存里只留这些证明的短行，剩下少数完整向量从 host 内存取；支持欧氏、cosine、内积与带过滤查询，且在更新下仍保持精确。4 块 H100 上，对 10 亿向量的 1 万个精确查询 **1.1 秒**完成（穷举需 5 分钟）；11 个开源 LLM 上取精确 top-10 attention key 比穷举快 **2.2–13.1×**；百万 token 的稀疏 attention 中比 FlashInfer 的 bf16 选择快 **3.1×**（后者多数 query 取不到精确 top-64）。
- **[BitShare: Sensitivity-Aware Binning and Bit Sharing for Compacting LLM Weight Storage](http://arxiv.org/abs/2611.28607v1)**（`2611.28607`，cs.LG/cs.AI/cs.ET，11-21）：小 batch 解码受带宽限制，每权重存多少位直接决定成本；分组量化让全组同精度，但组内输入通道的敏感度并不相同。BitShare 是无码本的权重格式：保留分组量化的整数网格与反量化器，但让组内精度可变——按敏感度把每组的通道分到三个 bin（位置固定），静态位共享配合最优位值分配，让不敏感的权重共享低位，且低位在每组或每对权重中只存一次；共享感知版的 GPTQ 决定每个存储值，无需微调、无码本。BITSHARE-U 每组布局相同、解码器按固定走线路由比特；BITSHARE-N 在同一位预算内逐组选布局。Pile 上标定、同等存储下，两种模式在 3-bit 与 2-bit 的 WikiText-2/C4 困惑度都低于 GPTQ；2-bit 下 BITSHARE-N 把 WikiText-2 困惑度相对 SliM-LLM 最多降低 **70%**、相对 GPTAQ 最多 **35%**；在 SliM-LLM 的 2-bit 困惑度水平上，BITSHARE-U 每权重少存 **13.6–19.4%** 的比特，DRAM 权重流量同比例下降。作者还给出在 SkyWater 130 nm 综合的硬件解码器，吞吐与 INT-n / SliM-LLM 解码器持平。
- **[Measuring GPU Memory Traffic on the NVIDIA GB10 Without C2C Telemetry](http://arxiv.org/abs/2611.29915v1)**（`2611.29915`，cs.AR/cs.DC/cs.PF，11-23）：DGX Spark 等设备用的 GB10 把 Arm CPU die 与 Blackwell GPU die 用 NVLink C2C 连起来，GPU 没有本地显存——每次 L2 miss 都要跨 C2C 访问挂在 CPU die 上的 LPDDR5X，但被测系统的软件没有暴露任何对应计数器。作者证明用 GPU 的五个 L2 sector 计数器即可：通过 CUPTI 采样接口每 10 ms 采一次，采样本进程无需挂到被测 workload 上，就能实时量出 GPU 显存流量，并把 copy engine 流量与 kernel 的读 miss/写区分开。对已知大小的大块流式传输，在 Acer GN100 上误差 **0.28%**、DGX Spark 上 **0.005%**，且与拷贝如何切分无关、会剔除 L2 命中的数据；自然的替代品 SMMU 计数器数的是地址翻译而非字节。应用于一台未改动的服务器：Mistral 7B 解码每 token 读 **13.47 GiB**（即其使用的权重加 KV cache），达到 NVIDIA 标称带宽的 **83%**。方法已作为开源工具发布。

> 本文是 [PTX 专栏](/ptx/) 第 9 期，对应官方文档 §5.1, §5.1.1–5.1.2。

## TL;DR

PTX 用**状态空间（state space）**这个概念，把 GPU 上形形色色的存储抽象成一组有名字的「区域」：`.reg`（寄存器）、`.sreg`（特殊寄存器）、`.const`、`.global`、`.local`、`.param`、`.shared`、`.tex`。每个状态空间由五个特征刻画——大小、可寻址性、访问速度、访问权限、共享级别。其中最关键的一列是**可寻址性**：寄存器 `.reg` 和特殊寄存器 `.sreg` 不可寻址，只能直接作操作数；其余空间都可寻址，得靠 `ld`/`st` 按地址访问。本期聚焦前两个空间：寄存器是「快、有限、会溢出」的私有存储，特殊寄存器是「只读、预定义」的平台寄存器。

## 一、概念铺垫：从「内存层级」到「状态空间」

第 3 期讲过内存层级——local、shared、global 谁看得见谁。那是**软件视角**：站在「数据放哪一层、能被谁访问」的角度。这一期换一个更底层的视角：PTX 在语法层面是怎么**命名和组织**这些存储的。答案就是**状态空间**。

状态空间是 PTX 最核心的抽象之一。它的定义一句话：**一个具有特定特征的存储区域，所有变量都住在某个状态空间里**。这些「特征」包括五个维度——大小、可寻址性（能不能取地址）、访问速度、访问权限（读/写/只读）、线程间共享级别。为什么需要这层抽象？因为 GPU 上的存储种类太多、特性各异：寄存器快但每线程私有，全局大但慢，共享介于两者之间……PTX 用一个统一的概念把它们框起来，让每条 `ld`/`st` 指令用后缀（`.global`、`.shared`……）声明自己访问哪一个，而不是让程序去猜。

所以这一章（§5.1）的任务，就是把「有哪些状态空间、各自什么属性」这张总表立起来，然后逐个空间展开。本期（第 9 期）讲总览，外加离计算单元最近的两个空间——寄存器 `.reg` 和特殊寄存器 `.sreg`；常量、全局、本地、参数留到第 10 期，共享和纹理留到第 11 期。

## 二、文档语义：§5.1 总览与两个寄存器空间

### §5.1 总览：八个状态空间，五维属性

PTX 一共定义了八个状态空间，先看它们是谁、干什么的（文档 Table 6）：

| 状态空间 | 描述 |
|----------|------|
| `.reg` | 寄存器，快 |
| `.sreg` | 特殊寄存器，只读、预定义、平台特定 |
| `.const` | 共享、只读内存 |
| `.global` | 全局内存，所有线程共享 |
| `.local` | 本地内存，每线程私有 |
| `.param` | 内核参数（每 grid）或函数/本地参数（每线程） |
| `.shared` | 可寻址内存，每 CTA，cluster 内线程可访问 |
| `.tex` | 全局纹理内存（已弃用） |

光看名字还不够，每个空间的「脾气」要靠下面这张属性表来区分（文档 Table 7，这是本节最重要的一张表）：

| 状态空间 | 可寻址 | 可初始化 | 访问 | 共享 |
|----------|--------|----------|------|------|
| `.reg` | 否 | 否 | 读/写 | 每线程 |
| `.sreg` | 否 | 否 | 只读 | 每 CTA |
| `.const` | 是 | 是 | 只读 | 每 grid |
| `.global` | 是 | 是 | 读/写 | context |
| `.local` | 是 | 否 | 读/写 | 每线程 |
| `.param`（内核入参） | 是 | 否 | 只读 | 每 grid |
| `.param`（函数内） | 受限 | 否 | 读/写 | 每线程 |
| `.shared` | 是 | 否 | 读/写 | 每 cluster |
| `.tex` | 否 | 是（经驱动） | 只读 | context |

这张表有四列，最该盯的是第一列**可寻址（addressable）**。它把八个空间劈成了两拨：**不可寻址**的只有 `.reg` 和 `.sreg`，其余都**可寻址**。可寻址意味着「这个变量有个地址，能用 `ld`/`st` 按地址去够它」；不可寻址意味着「它没有地址这个概念，只能直接拿名字当操作数」。这一刀砍下去，就解释了为什么前面几期反汇编里，寄存器 `%r1`、`%tid.x` 从来都是直接出现在指令里，而全局、共享的访问总要 `cvta`、`add` 算地址再 `ld`/`st`。

再看第四列**共享（sharing）**，它是一条从私到公的梯度：`.reg`、`.local` 是每线程私有，`.sreg` 每 CTA，`.const`、`.param` 每 grid，`.shared` 每 cluster，`.global`、`.tex` 是整个 context 共享。把共享级别和「离计算单元的距离」放一起看，就是一张经典的存储金字塔。

### §5.1.1 寄存器空间：快、有限、不可寻址、会溢出

寄存器（`.reg`）是离执行单元最近的存储，文档给了四个要点。

**其一，快，但有限。** 寄存器数量有限，而且因平台而异。一旦用超了，「寄存器变量会溢出（spill）到内存」，性能随之变化。每个架构都有推荐的寄存器用量上限（见 CUDA Programming Guide）——这是写 kernel 时要留意的硬约束。

**其二，可类型化，也可无类型。** 寄存器可以是有类型的（有符号整数、无符号整数、浮点、谓词），也可以是无类型（`.b` 位类型）。类型决定了指令怎么解释寄存器里的位。

**其三，大小受限。** 除谓词寄存器是 1 位外，标量寄存器宽度有 8、16、32、64、128 位，向量寄存器有 16、32、64、128 位。8 位寄存器最常见于 `ld`、`st`、`cvt` 指令，或作为向量元组的元素。

**其四，最关键的一点——不可寻址。** 文档原话：寄存器和其他状态空间的区别在于它们**不完全可寻址**，也就是说，**无法引用一个寄存器的地址**。你不能像对全局变量那样，取一个寄存器的地址、再按地址去访问它；寄存器只能直接以名字出现在操作数里。

此外还有两条编译层面的规矩：使用 ABI 编译时，寄存器变量限于函数作用域，不能声明在模块作用域；寄存器还可能有多字读写带来的对齐边界要求。

### §5.1.2 特殊寄存器空间：只读、预定义、平台特定

特殊寄存器（`.sreg`）这一节很短，就一句话：它存放**预定义的、平台特定的寄存器**，比如 grid、cluster、CTA、线程参数、时钟计数器、性能监控寄存器。**所有特殊寄存器都是预定义的**——你不能自己声明一个 `.sreg` 变量，只能用语言已经定义好的那些。

前面几期反复出现的 `%tid`（线程 id）、`%ctaid`（block id）就是特殊寄存器。它们只读（表里 Access 是 RO）、每 CTA 共享、不可寻址——你只能读它们的值，不能改、也不能取地址。这一期的反汇编还会见到另一个特殊寄存器 `%SPL`（栈指针）。

## 三、反汇编与讲解：一个内核踩遍五种状态空间

状态空间是抽象概念，最好的验证是找一个「一条龙」的内核，让它同时动到寄存器、特殊寄存器、参数、本地、全局五种空间。下面这个内核特意用了一个 64 元素的局部数组，逼编译器把它溢出到本地内存。

CUDA 源码：

```cuda
__global__ void spillKernel(int *out, const int *in, int n) {
    int a[64];
    for (int i = 0; i < 64; i++) a[i] = in[i];
    out[threadIdx.x] = a[n & 63];
}
```

真实 PTX（Compiler Explorer，NVCC 13.3.0，`-arch=sm_90a -ptx -O3`；中间大量重复的 `st.local` 已省略，指令原样摘录）：

```nasm
        mov.u64         %SPL, __local_depot0;            // 特殊寄存器 %SPL：指向本地内存基址
        ld.param.u64    %rd1, [spillKernel(...)_param_0]; // .param：读内核参数 out
        ld.param.u64    %rd2, [spillKernel(...)_param_1]; // .param：读内核参数 in
        ld.param.u32    %rd3, [spillKernel(...)_param_2]; // .param：读内核参数 n
        add.u64         %rd6, %SPL, 0;                   // 本地内存基址放进 %rd6
        ld.global.u32   %r1, [%rd4+12];                  // .global：读 in[i]
        ...
        st.local.v4.u32 [%rd6], {%r4, %r3, %r2, %r1};    // .local：4 个寄存器打包写进本地内存
        ...（重复 16 次，把 64 个 int 全部写进本地内存）
        ld.local.u32    %r65, [%rd10];                   // .local：按动态索引读回 a[n & 63]
        mov.u32         %r66, %tid.x;                    // .sreg：特殊寄存器 %tid.x
        st.global.u32   [%rd12], %r65;                   // .global：写 out[threadIdx.x]
        ret;
```

这段反汇编把五个状态空间串在一条链上，逐个看：

**`.reg` 寄存器：`%rd1`、`%r1` 到 `%r66`。** 这些名字直接出现在 `ld`、`st`、`add`、`mov` 的操作数位置，没有任何「取地址」的动作——这正是 §5.1.1 说的「不可寻址」：寄存器没有地址，只能当操作数。注意 `%r1` 一路编号到 `%r66`，编号这么大，恰恰说明这个内核的寄存器压力不小（下面会看到它溢出了）。

**`.sreg` 特殊寄存器：`%SPL` 和 `%tid.x`。** `mov.u64 %SPL, __local_depot0` 里的 `%SPL` 是栈指针，一个只读、预定义的特殊寄存器，编译器用它拿到本地内存的基址；`mov.u32 %r66, %tid.x` 里的 `%tid.x` 是我们熟面孔——线程 id。两者都是 `.sreg` 空间的，只读、用户不能定义。

**`.param` 参数空间：`ld.param.u64 %rd1, [..._param_0]`。** 内核的三个入参 `out`、`in`、`n` 都在 `.param` 空间，用 `ld.param` 读进来。参数空间的细节留到第 10 期，这里只需看到它作为「内核入参的容器」登场。

**`.local` 本地内存 + 寄存器溢出：`st.local.v4.u32 [%rd6], {%r4, %r3, %r2, %r1}`。** 这是本段最值得说的一行。源码里的 `int a[64]` 有 64 个 int（256 字节），远超出寄存器能容纳的量，而且后面用 `a[n & 63]` 动态索引——编译器既放不进寄存器、又无法静态确定访问哪个元素，于是把它「溢出（spill）」到本地内存：先 `ld.global` 从全局把 `in[i]` 读进寄存器，再用 `st.local.v4.u32` 把 4 个寄存器**打包**写进本地内存。`.v4.u32` 是 128 位向量寄存器（§5.1.1 说的「向量寄存器 128 位」），`{%r4, %r3, %r2, %r1}` 就是把 4 个 32 位寄存器拼成一个向量。这一来一去，就是 §5.1.1 那句「寄存器有限，超限溢出到内存」的活生生现场。

**`.global` 全局内存：`ld.global.u32` 和 `st.global.u32`。** 开头从 `in` 读数据、结尾把结果写进 `out`，走的都是全局空间。

把这五种空间串起来，就是这个内核的完整数据流：**全局**读入 → 暂存**寄存器** → 溢出到**本地** → 按索引从**本地**读回 → 用**特殊寄存器** `%tid.x` 算地址 → 写回**全局**。一条链，五站，全在这个反汇编里。

## 小结

- 状态空间是「具有特定特征的存储区域」的命名抽象，特征含大小、可寻址、速度、权限、共享五个维度。
- PTX 共八个状态空间：`.reg`、`.sreg`、`.const`、`.global`、`.local`、`.param`、`.shared`、`.tex`。
- 属性表最关键的一列是**可寻址性**：只有 `.reg`、`.sreg` 不可寻址，其余都可寻址。
- 寄存器 `.reg`：快、有限、会溢出、可类型化、大小受限（标量 8–128 位、谓词 1 位、向量 16–128 位）、**不可寻址**。
- 特殊寄存器 `.sreg`：只读、预定义、平台特定，如 `%tid`、`%SPL`。
- 真实反汇编里，一个内核串起 `.param`→`.reg`→`.local`→`.sreg`→`.global` 五种空间；`st.local.v4.u32` 是寄存器溢出的直接体现，`{%r4,%r3,%r2,%r1}` 是 128 位向量寄存器。

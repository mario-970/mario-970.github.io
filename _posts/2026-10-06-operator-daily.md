- **精度与确定性：Hopper 三角注意力与内存受限迭代法各给了一条可复用的做法**。**TurboPairFormer** 的**关键 tile 并行反向**让每个概率 tile 只为 query/key/value/pair-bias 四个梯度**重算一次**，用**有序部分归约**取代浮点原子加、也不再落盘完整 score 梯度，因此 **600 组输入 × 5 次重复调用下四个梯度逐位一致**；**输出残差补偿**保留 BF16 输出、却在 FP32 里更准地算反向修正，梯度 RMSE 再降 **28～47%**，OpenFold3 里 16 张 H100 上比其 Triton 后端快 **1.73×**。**CutBCE** 把大词表 BCE 的前向与反向**都做成片上算 logit tile** 的 Pallas kernel（自定义 VJP），8 芯 TPU 上峰值 HBM 降 **65.7%**、训练提速 **225.9%**；**混合精度矩阵分裂**则指出定常迭代法**受限于访存而非算力**，用半精度 + 迭代精化拿到 Jacobi **1.60×**、Gauss-Seidel **1.25×**，NASA OVERFLOW 的 SSOR 换精度后整体应用 **1.14×**。

## 三、arXiv 论文（算子内核）

**自动生成 kernel 的「第二问题」：怎么验证、怎么迁移**

- **[SyclKittens: A Tile Programming Model for Programmers and Coding Agents on Intel GPUs](https://arxiv.org/abs/2610.04277)**（`2610.04277`）：新加速器总是**先有硬件、后有让它跑得快的 kernel**，因为峰值性能要靠对操作数流水线与数据搬运的架构级经验。这篇问的是一个接口设计问题：给 coding agent 的接口应该**暴露机器原始能力**，还是**编码已知good方法**？控制实验很干净——三个 coding 模型、三个 kernel：给原始 SYCL 加执行反馈时，最强的 Opus 4.8 写出的单卡 GEMM 只到 Intel 调优过的 oneDNN 的 **57.5%**；换成 **SyclKittens**（硬件感知的 tile 编程模型，把操作数按 matrix-engine layout 摆放、走 L1 预取、并在连接 GPU stack 的 fabric 上通信）在**同样的 agent、任务与反馈预算**下到 **82.1%**。保留工作负载相关策略的可编程性后，人与 agent 联合调优的 kernel 套件在 GEMM 形状上几何平均到 oneDNN 的 **~96%**，单卡跑 Llama-3.1-8B 推理比 `torch.compile` 快 **1.59×**、比 oneCCL 上配平的多卡 decode 路径快至 **2.91×**。开源在 `github.com/intel/SyclKittens`。对算子组的价值是**方法论**：这等于把「架构手册里的隐式约定」从提示词挪进了**编程模型的类型系统与 API 形状**，agent 的产出上限随之改变——和 10-05 那期 D2K-Bench 的「瓶颈在设计发现而非写代码」正好互补：一个是给**指导**，一个是给**接口**。

- **[MetaKernelBench: Measuring GPU Kernel Knowledge Transfer Beyond Code](https://arxiv.org/abs/2610.05014)**（`2610.05014`）：现在做 kernel 优化的 agent 会把经验攒进知识库或蒸馏成技能，但**既有 benchmark 只给每次尝试的实现质量打分，从不衡量攒下来的经验有多少复用价值**。MetaKernelBench 测的就是这个：**74 个问题**（六个融合子图族），每个都配一对**只在 DSL 上不同**的 CuTe DSL 与 TIRx 版本；agent 先单跑一个变体，被要求把学到的东西蒸馏成**自然语言技能**，再把这段技能作为**唯一额外输入**喂给同一模型在另一个 DSL 上的尝试，逐次配对、预算配平。六个模型、两个方向的结果很不好看：配对增益区间 **-19% 到 +29%**，四个模型双向都涨，但**每个模型的每个方向上都有 16%～45% 的问题退化**；更关键的是结果**跟「源尝试相对目标单跑的表现」相关，而非「源是否成功」**——源强于目标时 **71%** 的比较有改善，源弱于目标时 **54%** 反而退化。对算子组的直接含义：**「跑通了」不等于「值得学」**，把失败尝试的教训一并入库、并按相对水平而非绝对成败决定是否迁移，是构造 kernel 技能库时绕不开的判据。

- **[RESOLVE: Language-Agnostic Validation of GPU Kernels Through Testing, Reduction, and Proof](https://arxiv.org/abs/2610.05683)**（`2610.05683`）：AI 已经能写生产级 GPU kernel，但**验证**没跟上——跑几个随机输入、比对参考实现在数值容差内，既**抓不到只在特定时序下触发的竞态**，容差本身又**会掩盖真 bug 并制造假阳性**（哪怕调过很多轮）。RESOLVE 用三段式把容差整个绕开：（1）**二进制插桩扰动执行时序**以暴露竞态；（2）agent 把候选与参考 kernel 都改写成「**降并发**」版本——更易于分析、但在所有测试下**输出逐位一致**；（3）在 **F\*/Pulse** 框架里形式化分析降并发版本，**证明二者在实数上做的是同一个计算**。能力面上：在 KernelBench 上验证了一批 kernel，并**跨 CUTLASS、Triton、Gluon 三个框架/语言证明融合 GEMM 的等价性**；对历来最难验证的 **mega-kernel** 也有办法，并挖出 **4 个此前未报告的问题，其中 2 个是明确 bug**；最后展示 agent 用 RESOLVE 把这些问题修掉且**性能影响极小**。对算子组这是本期最该通读的一篇：它给出的是一条**可自动化、不依赖容差**的 kernel 正确性流水线，也顺带说明**agent 只有在能严格自检时才敢激进优化**。

- **[SparseCraft: Agentic Hardware-Software Co-Optimization for Sparse Computing](https://arxiv.org/abs/2610.05037)**（`2610.05037`）：稀疏加速器的设计空间通常靠**解析模型**搜索，于是设计点被「模型预测的性能」而非「硬件实测性能」接受。SparseCraft 把语言模型塞进**闭环**（CHIA loop）：**15 轮迭代**里模型读上一轮实测结果，通过 MCP 工具服务器改写 Gemmini 加速器的 **Chisel RTL、存储配置与稀疏 kernel 调度**；任何候选都**必须过完 legality 检查、elaborate、周期精确仿真、逐位比对金标准、综合**才算数，失败则由第二个模型修。每个实测结果都被转成下一轮的工作单（诊断出的瓶颈 + 对应策略指导 + 已试设计的历史 + 模型自身预测的评分）。在 512×512 的 GraphChallenge 稀疏-DNN 层上，比 block-sparse Gemmini 基线：**周期数 2.1× 更少、片外流量 9.8× 更少、面积 22.8% 更小**，建模 perf/W **5.61×**、EDP **11.8×** 更低；收益跨三层——**保持稠密操作数常驻的调度**消掉了 9.8× 的流量，模型自己写的 **zero-gated MAC 与 zero-row skip 单元**压了能耗，缩存储减了面积。**边界**：交付物是 **RTL 与面积/功耗**，不是 GPU kernel——读它的价值在「**给实测而非预测建闭环**」这一条流程，以及 zero-gated MAC 这类**稀疏算子的门控思想**。

**低位宽与多精度格式**

- **[You Only Convert Twice: Ozaki Scheme II for Chained Tensor Mode Products](https://arxiv.org/abs/2610.05059)**（`2610.05059`）：Ozaki scheme II 是用 **INT8 Tensor Core** 做高精度矩阵乘的路线（把浮点拆成多个 INT8 残差分量再累加），但**链式张量缩并**时每一步都要在残差与浮点之间来回转换，开销吃掉了收益。**OzII-RescaleBE** 的做法是**全程留在残差表示里**：重标定（rescaling）与基扩充（base extension）**直接在残差上做**，于是**只在链首做一次转残差、链尾做一次重建**。实现用 **CuTe DSL + INT8 Tensor Core**，与逐模组合的 `GEMMul8-Composed`、稠密 Kronecker 形式的 `GEMMul8-KRON` 对比：三个不同输入分布的数据集上，**链深 d=3～7 的法向相对误差 2.5e-16～2.6e-15**（对照 `GEMMul8-KRON` 是 1e-16～1e-15、`GEMMul8-Composed` 与 FP64 链是 1e-16～3e-16），**d=8 时误差升到 7e-14～6e-13**；模大小 n=8～256 时吞吐 **1.47～4.42 GDoF/s**，n=8、12 时在 `GEMMul8-KRON` 的 **12% 以内**、更大尺寸上反超；对 `GEMMul8-Composed` 在 **n≤128 时是 2.1～60×** 吞吐，但 **n=256 时低 6～12%**，设备内存占用也更小。对算子组：这是一条**把「多分量精度仿真」的中间态固定在整数域**的工程结论，直接对应 dense/批量张量缩并里的**转换-累加流水线设计**——误差在 d=8 附近明显劣化，说明链长是有硬边界的。

- **[StagQ: Constraint-Driven Multi-Precision Weight Quantization for LLMs](https://arxiv.org/abs/2610.05977)**（`2610.05977`）：在一个机队里服务同一个 LLM 需要**好几个权重精度档位**，多精度格式的作用是**只存一份、其前缀本身就是合法的低精度码**，而不是存多份副本。StagQ 的主码流是「**2-bit 分组仿射基 + 可配置条数的 1-bit 细化平面**」，细化平面走**二进（dyadic）步长阶梯**；关键性质是**每档受支持的精度都是可读前缀**，解码用的仿射映射来自**所有精度共享的元数据**、**无需逐权重查表**；另有一份稀疏 side record 在格点拟合前后各填一次，专门兜住**网格服务得最差的那几个权重**。编码器给了两个配置：**2-bit 时**更省的那个在 Llama-3.1-8B、Phi-4、OLMo-2-7B 上比最强多精度基线高 **3.1～7.0 个 MMLU 点**（逻辑码率略低）；**3-bit 时**在 Llama-3.1-8B 领先、Phi-4 以更高码率领先、OLMo-2-7B 打平；**4-bit 时**三者都以更高码率打平。**难得的是它给了 kernel 计时**：NVIDIA A100 上 batch-1 矩阵-向量乘（合成权重），其 kernel 在**多数形状-精度组合**下快于两个基线 kernel。对算子组的看点是那个**「前缀可读」的格式约束**——它决定了**解量化 kernel 要按码流前缀分支**，而不是按精度档位跑不同 kernel。

- **[CentriQ: Calibration-Free Quantization of Diffusion Transformers via Exact Mean Centering](https://arxiv.org/abs/2610.06260)**（`2610.06260`）：4-bit（W4A4）是降 DiT 采样成本的主要手段，但既有方法两头不落地——**校准类**方法绑死了具体 checkpoint 与 prompt 分布，**免校准的 Hadamard 旋转**（在 LLM 上有效）在 DiT 上掉质量。这篇先给出**结构性原因**：**adaLN（自适应层归一化）条件化会给激活加上一个逐 token 均值**，而在被测 DiT 的宽度下，免校准方法所用的 Hadamard 旋转**无法把这个均值均匀铺到各坐标上**，于是**总有一个主导方向活过旋转并决定量化范围**。CentriQ 的对策很直接：**旋转前先把每个 token 中心化**，再用一个 **rank-1 全精度分支精确还原该均值**，因此逐 token 尺度可以**闭式给出、不需要任何数据**；权重则在**鲁棒 ℓp 目标**下拟合（跟踪每组的稠密模态、折掉重尾）。三个 DiT 上：4-bit 追平需校准的 **SVDQuant**；2-bit 权重上超越迄今最强的免校准方法；**并且是首个在 2-bit 激活下仍保持可用画质的免校准方法**。对算子组：**rank-1 全精度旁路**是新增的一小段算子，收益是**免掉校准数据与逐 checkpoint 重标定**——属于那种「多一个小算子、换掉整条校准流水线」的交易。

- **[RPFQ-ViT: Rotated Phase-Frame Quantization for Extremely Low-Bit Weights in Vision Transformers](https://arxiv.org/abs/2610.04457)**（`2610.04457`）：ViT 的高维线性投影与注意力仍然吃存储和推理开销，而**极低位宽**量化在 ViT 上往往掉得厉害——原因是**常规实值标量码本与 Transformer 投影的方向性几何不匹配**。RPFQ-ViT 把**成对的通道放进二维相位平面**量化，让低位码**更好地保住投影方向**，再用轻量缩放恢复幅度；它是 **`nn.Linear` 的 QAT 直接替换**，**不改动标准的实值注意力、归一化与激活计算图**。ImageNet-1K 上：ViT-B/16 在 **W2/A4** 下 79.33% Top-1 / 94.48% Top-5，Swin-T 在 W2/A8 下 79.30%，DeiT-S 在 W2/A8 下 77.41%；消融显示通道配对、可学习旋转、相位锚点学习、残差相位细化各自都贡献质量。落地到 iOS/Android 原生运行时：**2-bit 打包**后模型比 FP32 小 **5.4～7.1×**、端到端设备侧延迟降 **1.4～1.6×**。对算子组：**权重 2-bit 打包 + 相位解码**意味着 GEMV/GEMM 的**解量化路径要按成对通道处理**，而激活仍是 A4/A8——是典型的**权重侧激进、激活侧保守**组合。

- **[BARQ: Balanced Codebook Refinement for Low-Bit LLM Quantization](https://arxiv.org/abs/2610.04490)**（`2610.04490`）：码本式权重量化能同时降存储与**参数访存流量**，但拟合过程中**最近码字的分配不均衡**，会让部分码字**得不到足够更新**、码本利用率被卡住。BARQ 只做**码本拟合的再平衡**，不动编码结构：先通过**熵正则化的最优传输**（**均匀边缘约束** + **曲率加权重建代价**）算权重块与码字之间的**联合软分配**，保证精确解里**每个码字拿到相等的正拟合质量**；再用**分配加权的重心更新**细化码字，并**证明该更新在分配固定时最小化拟合目标**（有限次 Sinkhorn 迭代下，只要所有码字质量超过分母下限，实现仍保留该最优性）；最后**丢掉软分配**，用细化后的码本做**标准硬最近码字编码**，并给出**降低硬量化失真与评测损失**的充分条件。多个 LLM 上，在同等比特预算下**困惑度更低、平均零样本精度更高**。代码在 `github.com/chenhangcuisg-code/BARQ`。对算子组：收益全在**码本质量**上，故**运行时解码算子形态完全不变**（仍是查表 + 仿射重建），是一类零 kernel 改动成本的量化前处理——和 10-05 期 TaSQ 的「变换折进权重、运行时不变」同一路数。

- **[Loopy: Low-Bit Quantization Framework for Looped Language Models](https://arxiv.org/abs/2610.05265)**（`2610.05265`）：循环语言模型用**反复执行共享的循环核**来换取参数效率与测试时算力，PTQ 能降其内存与推理成本，但**被量化的共享核引入的误差会传到后续每一次循环**上。这篇的观察是：**通道缩放与正交旋转虽都保持浮点计算不变，产生的表示量化质量不同，而量化配置的候选排序会随循环深度变化**——所以**必须在目标部署深度上选配置**；可在这个深度上把整个校准集跑一遍太贵。Loopy 因此把共享核量化写成一个**循环深度感知的目标**，按**目标深度上的最终预测损失**来选共享的低比特表示，候选由通道缩放与正交旋转参数化；求解上**逐步把校准窗口分配给有希望的候选**（只做前向评估），同时**始终保持完整的目标深度执行**。八个设定上全面优于各基线：**Ouro-1.4B 在 W4A4 下 LAMBADA 困惑度比 SpinQuant 相对降 36.5%**。代码在 `github.com/Shameless0817/Loopy-review.git`。对算子组：W4A4 + **逐深度重选的量化参数**意味着同一份权重在不同循环轮次上可能用不同尺度——**权重量化参数的绑定粒度进了解码循环**，这是要单独算的账。

- **[TurboPairFormer: Fast and Stable Protein Folding Model Training with an Optimized Triangle Attention Kernel](https://arxiv.org/abs/2610.05854)**（`2610.05854`）：三角注意力是 AlphaFold3 系生物分子模型的核心计算，成本随 token 数**三次增长**；它特有的**共享 pair bias** 在常规的 query/key 归约之外**又加了一次跨注意力切片的归约**。作者考察的开源后端用三种办法应付这些归约，各有硬伤：**反复重算概率、浮点原子加、或完整落盘 score 梯度**；此外**从 BF16 舍入后的前向输出去算 softmax 反向修正，本身就在丢精度**。**TurboPairFormer** 是 NVIDIA **Hopper** 上的三角注意力实现，正面解决这两处：其**关键 tile 并行反向**算法让每个概率 tile **只为 query、key、value 与 pair-bias 四个梯度各重算一次**，并用**有序部分归约**实现**确定性累加——不用浮点原子、也不落盘完整 score 梯度**；**输出残差补偿**则保留一份 BF16 输出的舍入残差近似，在 **FP32 里更准地算反向修正，而前向输出仍是 BF16 不变**。crop 尺寸 384/640/768、head 维度 16/32 时，其 query/key/pair-bias 的**平均梯度 RMSE 在对比实现中最低**（对照 FP64 参考），受控消融中残差补偿把 RMSE 再降 **28～47%**；**600 组输入、5 次重复调用下四个梯度全部逐位一致**（固定执行条件）。集成进 OpenFold3（连带其三角乘 kernel）后，**16 张 H100 上每个优化步的 GPU 计算时间在评测配置里最低**，crop 768 时比 OpenFold3 的 **Triton 后端快 1.73×**、比 **cuEquivariance 快 1.13×**。对算子组：这是「**浮点原子加换有序归约 = 用一点带宽换确定性**」的一个干净样本，而**逐位可复现**在训练侧是可验证性的前置条件。

- **[Cut Binary Cross Entropy: Efficient Large-Vocabulary Loss and Gradient Kernels for Sequential Recommendation](https://arxiv.org/abs/2610.05559)**（`2610.05559`）：工业级序列推荐跑在 10^5～10^7 量级的物品目录上，多标签模型用**全词表 BCE** 训练，而标准 BCE 会**在 HBM 里物化一个稠密的 [B, N, V] logits 张量**，O(NBV) 的内存直接把训练打爆成 OOM。LLM 侧的 **Softmax** CE 早有分块优化，**大规模多标签 BCE 的优化在深度学习生态里基本没人做过**。**CutBCE** 是 JAX + Pallas 实现的**精确、硬件加速的 BCE 损失与梯度算子**，四件事：（1）**精确的融合重表述**——稠密背景损失 + 稀疏目标修正，而不是近似；（2）**自定义 VJP** 加配套的 **Pallas TPU 反向 kernel**，让**前向与反向都只把 logit tile 留在片上**，logits 及其梯度**永不落 HBM**；（3）**动态 VMEM 预算**与**分片感知的集合通信提升（collective hoisting）**以适配分布式 mesh；（4）**基于计数的零开销训练指标**。单芯 **TPU v5e/v6e** 小基准上消除 OOM、最高 **91.9%** 加速；8 芯 TPU slice 上训练 876k 物品的多标签 SASRec（Yambda-50M）：**峰值 HBM 降 65.7%**（每芯省下 >14 GiB）、**训练速度提升 225.9%**，精度相当。开源在 `github.com/AI-Hypercomputer/RecML`。对算子组：即便目标是 TPU/Pallas，其手法——**用「稠密背景 + 稀疏修正」的精确重表述换一次算子融合**、以及**为反向单独写 kernel 以保住片上 tile**——是可以直接平移到 GPU 损失算子上的。

- **[A Mixed-Precision Model for Matrix-Splitting Methods](https://arxiv.org/abs/2610.06414)**（`2610.06414`）：定常迭代法（Jacobi / Gauss-Seidel / SSOR 这类矩阵分裂迭代）**性能受限于访存，而非算力**——算术强度太低。这篇提出用**混合精度降低数据搬运量**，并在理论与实验两侧说明：该技术**一般能以与全精度迭代相近的速率收敛**（取决于所用精度与 **M 矩阵的条件数**）；而且可以用**迭代精化把解提回完整双精度**精度。实测：**半精度 + 双精度**混用，对 scalar 与 block Jacobi 平均比统一双精度快 **1.60×**、对 scalar 与 block Gauss-Seidel 快 **1.25×**；进一步把 **NASA 可压缩流体力学程序 OVERFLOW** 里 SSOR 迭代的精度降低，拿到**整体应用 1.14×** 的加速。对算子组：这是**「算力够、带宽不够」场景下换精度的标准账**——注意它的收益标定方式是**整体应用加速（1.14×）**而非单 kernel，因为迭代法的外层收敛行为会部分吃掉内层加速。

- **[FlashCart: Fast Cartesian Tensor Products for Equivariant Interatomic Potentials](https://arxiv.org/abs/2610.06409)**（`2610.06409`）：机器学习原子间势把原子模拟推到了电子结构方法够不到的时间与尺度，但**等变架构的计算成本**限制了它能表示的局域关联阶数、也即精度上限。FlashCart 让**高阶关联变得可负担**：把张量积**在独立的笛卡尔分量上展开**、**符号化地化简这些分量及其导数**，从而**生成融合 kernel**——作者称其**常常超过优化过的球谐（spherical）对照实现**；配合一个**递归构建等变特征、每步压到固定宽度**的架构，还给出一个反直觉结论：**提高关联阶数比增加宽度、深度或张量秩更划算**。在 **SPICE-MACE-OFF** 上推进了实测的精度-效率前沿：一个 **5.6M 参数**的 FlashCart 模型**能量与力误差更低**，同时比一个 **189M 参数的 transformer 推理快 10×**。对算子组：值得学的是**「符号化简 → 生成融合 kernel」**这条路径——针对固定的小维度张量积，**把化简做在编译期**往往比在运行时写通用 kernel 更有效，这与 CUTLASS/CuTe 里「针对具体形状生成特化 kernel」的思路同源。

- **[OVAL: Output-Aware Local Page Bases for KV Cache Retrieval](https://arxiv.org/abs/2610.06686)**（`2610.06686`）：长上下文推理里注意力的成本随 KV cache 增长，**page sparse attention** 通过**把每个 KV page 紧凑表示、再为每个 query 只检索一部分**来降本。既有检索方法的目标都是**估计注意力分数或 page 相关性**，但它们的优化目标**并不直接对应「近似误差如何影响最终按 value 加权的注意力输出」**。**OVAL** 提出一种**输出感知的 page 编码**：从 **key 与 value 的联合结构**导出，同时**保住检索所需的 key 信息**；它是**训练无关**的，推理时**不需要额外的、依赖 value 的统计量**；一旦构建完成，其**存储表示的大小与解码期打分成本都与「仅 key 的谱表示」相同**。在长推理、长上下文理解、长生成三类基准上：一致优于**仅 key 谱表示**基线，并与近期 KV cache 压缩/检索方法**有竞争力**；长推理上跨模型-基准对的 avg@k 表现强，若干长上下文理解与生成设定上以**适度的解码开销**追平或超过领先基线。代码在 `github.com/Ashkan13776/oval-kv`。对算子组：看点是**「编码里带 value 信息、但运行时开销与纯 key 方案持平」**——page 编码在离线/预填充期算掉，**热路径只多一个同样的打分 kernel**。

## TL;DR

- **低精度算子向 MoE 与 RL 后训练渗透**：GC-MoE 用 CUDA Green Contexts 把 dispatch 与 GEMM 拆到独立资源分区，FP8/FP4 grouped GEMM 在 8×B300 上比 DeepGEMM Mega MoE 快 **1.106×**（融合共享专家 1.123×）；EpiLoRA 把 LoRA 上投影塞进 FP8 GEMM 的 epilogue，单 adapter 每 token 时间降 **24%**；FourSight 用 fused SpliceGEMM 把 NVFP4 RL 的步时压在 FP4 基线的 **2.3%** 以内。
- **KV cache 压到 0.25–2.5 bit**：LoopVQ 跨 loop 联合做向量量化，0.5 bit 即超过标准 KV VQ，SGLang 峰值吞吐最高 **6.1×**；LoopKV 按 (loop, layer) 分档 2/4 bit 并共用一个 fused kernel，同延迟目标下 goodput 是 KIVI-4 的 **1.7–2.2×**；FlagRot 只旋转需要的 32 通道，2.5 bit 下把 KIVI 的 12 模型 KL 从 18.7 降到 **12.4×10⁻³**。
- **kernel 工程工具链继续成熟**：ForgeKernel 跨 run 积累硬件机制知识，Hopper/Blackwell 上几何平均超专家参考 **10%**，Ascend 910C 上超公开最优 **25.1%**；Warpline 不重编译、直接把探针插进二进制，B200 上 35 个 kernel 的中位开销仅 **1.2%**，且不改动 99.9% 的已执行指令。

### 低精度与量化 kernel

- **[GC-MoE: Overlapping Expert-Parallel Token Dispatch with FP8/FP4 Grouped GEMM via CUDA Green Contexts](http://arxiv.org/abs/2611.04222v1)**（`2611.04222`，cs.DC/cs.AI/cs.AR/cs.LG/cs.PF，11-03）：MoE decode 每层都要走 all-to-all dispatch、grouped GEMM 和 combine，而 DeepGEMM Mega MoE 这类融合算子把 dispatch 与计算放在同一 SM 上争抢寄存器、共享内存和发射槽，每次 replay 还要 workspace 清理与跨 rank barrier。GC-MoE 用 CUDA Green Contexts 把设备切成小的通信分区和大的计算分区，每个角色独立 kernel、独立资源预算与同步域；三段 CUDA Graph（Hopper 上因融合共享专家变四段）把 dispatch 与 grouped GEMM 作为并发根，token-ring 握手让首批 ring block 就绪即开始计算，双缓冲接收计数去掉尾部的跨 rank barrier。计算侧在 Blackwell 用 operand-swapped tcgen05 block-scaled MMA，在 Hopper 用 register-A WGMMA 加寄存器内 FP4 解码，并融合 SwiGLU、requant 与可选共享专家。8×H20 上 DeepSeek-V4.1-Flash decode 平均快 **1.188×**（峰值 1.296× / 1.353×）；8×B300 上 GLM-5.2 与 DeepSeek-V4.1-Flash 快 **1.106×**（融合共享专家 1.123×，峰值 1.209×），在全部 54 个测点上同精度胜过 Mega MoE，且 B300 的 148 个 SM 只为 dispatch 留 **20 个**。
- **[EpiLoRA: Fusing Many LoRA Adapters into Low-Precision GEMMs for Serving and RL](http://arxiv.org/abs/2611.03899v1)**（`2611.03899`，cs.DC/cs.CL/cs.LG，11-02 晚到补录）：底座模型转成 FP8/FP4 后 GEMM 变便宜，但 LoRA 仍作为旁路小 kernel 串行执行，在 decode 步里占比越来越高。关键观察是 GEMM 直到 epilogue 写输出时才需要 down-projection 的结果：EpiLoRA 先发射 down-projection，再把低精度 GEMM 作为依赖 kernel 发射、边流式加载权重，并在 epilogue 里为每个 tenant 加上 up-projection。作为 vLLM 插件，Hopper 上单 adapter 比 vLLM 最快配置每 token 时间低 **24%**，也快于 SGLang 与 TensorRT-LLM；多租户下 adapter kernel 在多数 GPU-模型组合上吞吐高于 vLLM。同一 FP8 底座还能直接训练：RL trainer 不再需要 16-bit 副本，27B 模型可在单张 **48 GB** GPU 上训练。
- **[FourSight: Stable FP4 RL Post-Training via Sequence Filtering and Sparse Channel Compensation](http://arxiv.org/abs/2611.04887v1)**（`2611.04887`，cs.AI/cs.LG，11-03）：NVFP4 的 W4A4 已成为 RL 后训练的目标部署格式，但量化会放大 rollout 质量损失与训练-推理不匹配（TIM），且这些失败并不均匀——严重漂移的 tail token 集中在少数 outlier 序列，量化误差集中在少数高方差激活通道。FourSight 用 TIM-aware 序列过滤把漂移轨迹排除在策略更新之外，并做稀疏精度补偿：只把 top-variance 通道留在 BF16，其余保持原生 NVFP4；配套 fused **SpliceGEMM** kernel，prefill 与 decode 走不同数据通路以压低开销。在多个模型与引擎上保持接近 BF16 的精度与 FP4 部署质量，step-to-accuracy 提升 **1.76–2.60×**，到 120B 规模步时仍在 FP4 基线的 **2.3%** 以内。
- **[FlagRot: Selective Rotation for Low-Bit KV Caches](http://arxiv.org/abs/2611.03992v1)**（`2611.03992`，cs.CL/cs.AI/cs.LG，11-02 晚到补录）：2-bit KV 能省约六倍显存，前提是误差可控；常规做法是量化前无条件旋转 key，但旋转会把尖峰摊平，也可能给平坦的 key 制造新峰，同一 key 内两种情况并存。FlagRot 把每个 32 通道片段分别存成「旋转」或「原样」，按标定后的 attention 误差二选一，读取时改为旋转 query。决策粒度跟随量化轴：KIVI 这类 per-channel cache 每 head 只需一次决策且无写入开销，per-token cache 则逐 key 决策，选择位塞进已有的符号位。2.5 bit 下把 KIVI 的 12 模型 KL 从 **18.7 降到 12.4×10⁻³**，在 9/12 模型上优于 RotateKV；作为 vLLM 插件把 128K 的 RULER 提高 **2.9 个点**，LongBench v1 均值提高 **0.4–1.9 个点**，并同样降低 4-bit 整数与 FP4 cache 的误差。
- **[LoopVQ: Sub 1-bit KV Cache Quantization for Looped Transformers](http://arxiv.org/abs/2611.05304v1)**（`2611.05304`，cs.LG/cs.AI/cs.CL，11-03）：looped transformer 复用同一组层，参数量省了，但每个 loop step 都各自存 KV，cache 随 loop 数线性增长成为主瓶颈。作者发现 loop 轴上的 KV 高度冗余、各 step 对量化的敏感度差异很大；LoopVQ 把多个 loop step 的通道联合编码，再微调 codebook 去对齐全精度输出。**0.5 bit/element** 即优于面向标准 LLM 的 KV 向量量化方法，在通用、长 CoT 推理与长上下文检索任务上均成立；与 TaSQ 组合后在 **0.25 bit** 仍保住大部分 BF16 精度。已在 SGLang 中实现，32K 上下文下 decode 延迟接近减半，1.4B / 2.6B Ouro 的峰值服务吞吐相对 BF16 分别最高 **4.3× / 6.1×**。
- **[LoopKV: Loop-Aware KV Cache Compression for Serving Looped Transformers](http://arxiv.org/abs/2611.04137v1)**（`2611.04137`，cs.LG/cs.CL/cs.DC，11-03）：Ouro 这类每个 loop 各存一份 KV 的模型，统一位宽或按 loop 固定规则都无法贴合每个 (loop, layer) 单元的实际敏感度——实测各单元单独损伤之和可近似总输出损伤，越靠后的 loop 越能容忍共享。LoopKV 用一次性离线 profile 为每个单元选择 4-bit、2-bit 或复用最后一个 loop 的 KV，规划器在预测损伤与存储预算下最小化读取量；decode 时每个 loop 先读 4-bit 值的高 2 位，只在自身 attention 权重需要时才取低位。整个方案由 vLLM 里的**单个 fused kernel** 执行。单张 RTX PRO 6000 服务 Ouro-1.4B，在 16K 最大长度、有延迟 SLO 的条件下，KV 比统一 4-bit 的 KIVI-4 少存 **35%**，goodput 是后者的 **1.7–2.2×**，六个公开基准均值均未显著低于 BF16。
- **[What Does 4-Bit Microscaling Cost a Wearable Activity Recognizer?](http://arxiv.org/abs/2611.04185v1)**（`2611.04185`，cs.LG，11-03）：用一个 15.9 万参数的 1D CNN 做腕部加速度动作识别，逐 fold 比较 MXFP4 与 NVFP4。FP16 与 INT8 相对全精度最多只掉 **0.16 个点**；只量化权重时 MXFP4 掉 **1.45** 点、NVFP4 掉 **0.72** 点；权重与激活都量化到 4 bit 后，MXFP4 掉 **5.14** 点而 NVFP4 只掉 **0.75** 点，后者在五个留出玩家 fold 上全胜。根因不在 block size 而在 **scale 选择**：参考 MXFP4 转换把 scale 向下取整，容易选出过小的 scale 导致 block 内最大值被裁掉；改为向上取整在 32/16 值 block 上分别找回 **3.18 / 3.63** 点，再换成 8-bit 浮点 scale（NVFP4 的做法）又加 **0.84 / 1.20** 点，而 block size 的影响不一致。对写 MXFP4/FP4 量化 kernel 的人来说，scale 的舍入方向比 block 大小更值得盯。

### Attention 与稀疏 kernel

- **[Multi-layer Indexer: Overlapping Selection and Attention in DeepSeek Sparse Attention](http://arxiv.org/abs/2611.03768v1)**（`2611.03768`，cs.LG/cs.AI，11-02 晚到补录）：DeepSeek Sparse Attention 每层前面都有一个 lightning indexer 扫全量 cache、保留 top-k=2048 个 token；长上下文下 decode 时间主要花在这个 indexer 扫描，而不是它喂给的稀疏 attention。作者观察到相邻层选出的 token 几乎相同，于是让某一层直接沿用上一层 indexer 的选择，从而解除依赖，使每个 indexer 能与其所属层的 attention 并发执行。这套 Multi-layer Indexer 无需重训、不新增权重，默认实现不改 kernel，直接跑在 SGLang 的生产 decode graph 里；另有可选的 fused decode kernel 在 DeepSeek-V3.2 上进一步加速。与 IndexCache（GLM-5.2 以 IndexShare 形式发布）组合时，IndexCache 砍掉部分层的 indexer，MLI 把剩余层的扫描藏起来：同等 retention 下，1/2 时 DeepSeek-V3.2 快 **14.5%**、GLM-5 快 **9.8%**，1/4 时分别快 **7.9% / 5.1%**；128K 下 1/4 retention 达到未改模型 decode 吞吐的 **1.32×**，高于 IndexCache 在 1/8 时的 1.28×，而精度与 IndexCache 相差几个百分点内。
- **[Coarse Semantic Blocks for Efficient Training-Free Sparse Attention](http://arxiv.org/abs/2611.04313v1)**（`2611.04313`，cs.LG/cs.AI/cs.CL，11-03）：一种无需训练的稀疏 attention：为每个 prompt 建 key 索引，把 key 聚成跨非连续位置的大语义 block，每个 query 对 block 质心打分后只 attend 选中 block 内的原始 K/V；选中同一 block 的 query 成组处理，因此即使每个 query 各自选块，prefill 仍然快。block 越大，质心打分与成组处理越便宜，同一时间预算下每个 query 反而能看更多 token——更大的 block 与更大的 token 预算可以同时更快、更准。在单张 H200 上测 Qwen3.5-4B 与 35B-A3B，含建索引与使用索引的全部开销，512K 时整模型墙钟相对 dense attention 加速 **2.3–2.4×**（prefill）与 **1.7–2.0×**（decode），1M 时 prefill 达 **2.9–3.0×**；35B-A3B 在 1M 内五个 RULER 任务、LongBench-v2 总体与 256K 内 MRCR 上都接近 dense，4B 主要在多 key 检索上掉点，但 512K 下三项基准仍优于延迟相近的 dense Qwen3.5-2B。
- **[LeanSparse: Memory-Efficient Serving for Native Sparse-Attention LLMs](http://arxiv.org/abs/2611.04671v1)**（`2611.04671`，cs.DC，11-03）：原生稀疏 attention 虽限制了每个 query 读取的历史，长上下文服务仍受 GPU 显存约束——现有 KV offload 系统把完整的 indexer key 历史留在 GPU 上，压低 decode 并发；prefill 的临时显存需求还会拖慢 admission。LeanSparse 利用两点：prefill 逐层消费历史，decode 可在比较原始 indexer score 前先筛候选。prefill 时用两个可复用的 GPU buffer 流式搬运每层历史，与模型计算重叠；decode 时做 coarse-to-fine 索引，先在紧凑表示上搜、只对候选取回原始 indexer key 精算；indexer key cache 与 KV cache 分开以跨生成步复用。在 SGLang 上以 DeepSeek-V4-Flash 实测，950K 上下文支持 **2.95×** 的并发请求、decode 吞吐是 HiSparse 的 **2.14×**；多轮 Open-SWE trace 上中位 TTFT 从 **21.6 s 降到 0.6 s**，中位 session 完成时间相对 ECHO 降 **17.7%**。

### 数值与 kernel 工程

- **[Adaptive accuracy-driven splitting in Ozaki matrix multiplication and application to block LU factorization](http://arxiv.org/abs/2611.03158v1)**（`2611.03158`，math.NA，11-02 晚到补录）：Ozaki 方案用一串低精度矩阵乘拼出高精度结果，精度与成本都取决于拆分份数；现有实现多按固定份数或经验规则。作者给出面向矩阵乘与 block LU trailing update 的精度驱动判据：矩阵乘推导 normwise 与 componentwise 两种「达到给定精度需要几份拆积」的准则；block LU 给出几乎无选择开销的固定 normwise 策略、可在后续 trailing update 减少份数的 LU-aware 自适应 normwise 策略，以及利用前序更新累积信息的 componentwise 策略（超出最大份数时退回普通矩阵乘）。同时给出严格的 backward error 界。数值实验显示自适应 normwise 能在保持 normwise 精度的同时减少拆分数，componentwise 在需要更强局部精度时给出更小的 componentwise backward error。
- **[EvoCG: Self-Evolving Precision Control for Faster Conjugate Gradient](http://arxiv.org/abs/2611.04469v1)**（`2611.04469`，cs.DC，11-03）：GPU 低精度吞吐远高于 FP64，但共轭梯度对降精度的容忍度随 Krylov 状态演化，固定精度策略很难吃满。EvoCG 把 tile 级精度当作在线控制动作：循环内的 RL 策略根据当前 solver 状态为每个 tile 选精度，并与 **Tile-CSC 统一混合精度 SpMV kernel** 及低开销的 in-loop runtime 协同设计，使决策真正换来速度。在 8 个科学领域的 47 个 SPD 矩阵上，相对 cuSPARSE / PETSc / Ginkgo / Mille-FP64 / Mille-Mixed 的几何平均加速为 **2.52× / 3.06× / 2.48× / 1.93× / 6.99×**；同一基座上比 EvoCG-FP64 快 **1.28×**，只多 **11.4%** 迭代、**1.09%** 开销，最终真残差范数与 FP64 几乎一致；Jacobi 预条件无需重训即可迁移，再快 **1.15×**。
- **[ForgeKernel: Self-Evolving Kernels Catching and Surpassing Experts and Agents](http://arxiv.org/abs/2611.04998v1)**（`2611.04998`，cs.DC，11-03）：现有 kernel agent 每次运行都从同一份初始知识起步，后续迭代也基本困在早期定下的架构里，缺少跨 run 的知识积累与架构演进。ForgeKernel 分析高性能参考 kernel 的硬件行为，把验证过的架构决策提炼成可复用的「硬件机制」知识而非模仿源码；一个 kernel 通过正确性与性能校验后会被封存，作为下一轮优化的新参考，使架构决策可以重访。在 Hopper 与 Blackwell 的 27 个算子、29 组输入配置上，25 组达到或超过专家参考，几何平均增益 **10%**；Ascend 910C 上在 CANN-Bench Season 1 决赛全部 8 个 level-4 算子的公开用例集上超过逐算子公开最优，几何平均 **25.1%**，全量提交在 A3 榜第一；截至 **2026-10-30**，ForgeKernel 生成的公开提交在 CANN-Bench 2.0 的三张 solution 榜（910C / 950DT / 950PR）与 SOL-ExecBench FlashInfer-Bench track 上均列第一。
- **[Warpline: Binary-Level Tracing and Unified Evidence for Agentic GPU Kernel Optimization](http://arxiv.org/abs/2611.04331v1)**（`2611.04331`，cs.PF/cs.PL，11-03）：LLM agent 已经在写 GPU kernel，但调优时看不到时间花在哪：硬件 profiler 只报各单元多忙，intra-kernel tracer 需要手工插桩并重新编译，而重编译本身就会改变被测 kernel。Warpline 分析二进制决定记录哪些事件，把探针直接插进二进制，无需重编译与人工步骤，再把 trace 与硬件 profiling 数据对齐到统一时间线。因为只需二进制，它能为 kernel 的每个新版本在任意编辑层级（source / IR / PTX）重新生成证据，也能追踪闭源 kernel。B200 上 35 个 Triton / CuTe DSL / CUDA C++ kernel，中位开销 **1.2%**，中位 **99.9%** 的已执行指令保持不变；现有 tracer 的中位开销为 1.6%–13.2%，仅保留 4.6%–32.7% 指令不变。10 个 SOL-ExecBench 问题上，使用 Warpline 的 agent 比裸 coding agent 与 NVIDIA KDA 花更少时间和模型请求，却每轮几何平均都领先，最终 **7.69×** 加速（对照 6.94×、6.13×）；两个 case study 显示它能暴露隐藏瓶颈并给出可执行的优化线索。
- **[Beyond Compression Ratio: High-Throughput KV Compression for Disaggregated LLM Serving](http://arxiv.org/abs/2611.04382v1)**（`2611.04382`，cs.DC，11-03）：分离式 serving 里 KV 压缩能减少通信量，但在高带宽互联上，压缩流水本身执行得不够快会把省下的通信时间又吃掉。该工作把分布变换与低比特量化两个阶段融合进一个 **KV-aware TileLang kernel**，消除中间 tensor 物化与冗余访存；同时把原来的无损压缩后端换成基于 LC 的可扩展、可搜索后端，以构成高性能压缩算子流水。融合 kernel 最高 **5.9×** 加速，无损后端吞吐从 **<90 GB/s 提升到 >500 GB/s**，端到端 job 完成时间最多降 **2.04×**，使 KV 压缩在高带宽网络下仍保留实际通信收益。
- **[Deep Learning Compilers: Architecture, Optimization, and Empirical Characterization](http://arxiv.org/abs/2611.04273v1)**（`2611.04273`，cs.LG/cs.AR，11-03）：系统梳理 DL 编译器的 frontend / middle-end / backend 架构、编译流程与各阶段优化技术，重点放在 middle-end 如何把高层模型表示接到硬件相关优化上；除架构分析外还做了实证刻画。在 NVIDIA RTX A6000 上用 PyTorch/TorchInductor 测到：编译器收益强烈依赖工作负载，融合友好的计算图最高 **8.21×**，其他工作负载提升有限；编译开销需要**数千次执行**才能摊销；dynamic-shape 编译把累计的 shape 切换成本降低约 **70%**，代价是稳态性能小幅下降。对算子开发者而言，这组数据给出了「什么时候值得让编译器融合、什么时候该手写 kernel」的量化边界。
